Context Window Architecture

A specification for assembling every model call from typed slots. This page is the normative text, and anything on the landing page, in the producer guide, or in the evidence notes that disagrees with it is wrong. Requirements are numbered from R-1; new ones append, and numbers are permanent and never reused.

Status: draft. Not yet stable. Generated requirement reference: SPEC.md. JSON contracts: items · traces · conflict groups · reason codes. Licence: free to implement, no attribution required.

1

Conformance

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119. MUST is required for conformance; SHOULD is expected unless a reason is recorded; MAY is optional.

A conformant assembler meets every MUST an assembler can meet by itself, and can emit its trace as JSON with the fields R-21 lists. A conformant producer meets every MUST in section 2, plus the ones aimed at producers of its kind: R-9 and R-14 for memory, R-10 for anything carrying user-controlled or fetched content, R-13 for retrievers, R-15 for MCP adapters, and R-18 for anything that supplies variants. A conformant application uses a conformant assembler and only conformant producers, and meets the MUSTs no component can meet for it: it enforces invariants, tool permissions among them, outside the model (R-5, R-15), writes state (R-8), declares conflict groups (R-11), authenticates each producer and binds its identity outside the items (R-15), makes every external read, retrieval and model call before it freezes the snapshot (R-12, R-23), versions its profiles (R-20) and deploys only evaluated ones (R-19). It renders with a renderer the published cases cover, and hands the payload to the model with each text in the platform role its renderer assigns, text assigned none in the live user turn, and no text of its own (R-7, R-16). The Assembler page marks each requirement as assembler, boundary or application, so you can see who owns which part.

These are the only claims this specification defines. An application is not conformant because one of its parts is, though it may say which of its parts are. The claims also differ in kind. Producer and application conformance is an agreement about what each emits and does. Assembly cannot confirm all of it, so the claim rests on their word, and an assembler's boundary checks catch only some breaches. An assembler's conformance concerns what it decides. A wrong decision fails silently, because a model accepts any payload, so the claim rests on evidence: a conformance report showing that the assembler passes every published case and rejects every published rejection for the tokenizers and renderers it provides, as Reporting results in conformance/README.md describes. An application's claim includes its assembler's, which is why it must render with a renderer the published cases cover: that assembler's report then backs how the payload is built, while the handoff to the model rests on the application's word like the rest of its claim.

Requirements are numbered R-n in a single flat sequence. A number is assigned once and never reused. A withdrawn requirement keeps its number and is marked withdrawn in the index. Other pages on this site, and the reference implementation, cite requirements by number.

The published JSON Schemas define item and trace field shapes. Profiles define model-request rendering; wire encodings must preserve these semantics. The website tools check structure and selected local invariants, not full implementation conformance.

A model call is assembled from items. Every item belongs to exactly one slot; slots are grouped into four planes. The planes answer four different questions and are never merged. An item in one of the two evidence slots is an evidence item, and the piece of a document a retriever pulls is a chunk.

3

Governance

Rule zero
Language guidance goes in context, and enforceable invariants go outside the model. "Never quote an unverified price" is stated in governance and enforced by a tool guard: the model is instructed, but the application still enforces the rule.
3.1 Instruction authority and data roles
{{ a.n }} {{ a.name }}{{ a.value }} {{ a.text }}

These seven values are the complete set, and the monospaced one under each name is what goes in the authority field. Only governing and user items can direct behavior: governing instructions, the live query, and the user's own earlier turns in history. Prior model turns carry untrusted, so they can't. Authority alone decides this: an item's trust and injection_risk never add or remove it (R-6). The other five values say where data came from. They aren't a ranking of which facts are true. An item with any other authority value is excluded at admission.

Slots never override platform message roles or application controls. A retrieved document is not an instruction because it contains imperatives. A preference does not lift a safety constraint. Tool output is evidence, not permission to act.

3.2 State is not memory
state.*

State is canonical, structured, typed, current, and owned by the application. It holds workflow stage, approval status, selected entity IDs, pending action, and retry count. The database is the source of truth, never the model.

interaction.memory

Memory is fallible, compressible, linked to its source, and revocable. It holds preferences, prior-discussion summaries, and inferred long-term facts. Every entry carries an expires deadline and the turn it came from.

3.3 Conflict resolution · instruction rules and factual route policy
{{ c.when }} → {{ c.then }}

Instruction conflicts: platform roles and application controls first, governing instructions over user requests, then the peers' own conflict policies. The peers are the members at the highest authority in the group that can instruct: governing, or user if no governing item is there. A group left with fewer than two admitted members is moot. Otherwise, a group with one peer or none is decided by authority, and nothing is excluded. If exactly one of two or more peers says governs and the rest say defers, the deferring ones are excluded. Items with any other authority, which covers every state, evidence and memory item and anything carrying untrusted, never become instructions, whatever their wording; they stay as material. Anything else escalates to the route's on_unresolved_instruction action.

Factual conflicts: route policy for the group's fact key lists the eligible producers, by authenticated identity, in precedence order, and the scope keys a claim must carry. It may prefer a verified current observation over a stale document by listing that producer first, but no data role automatically wins, and an item's trust, its injection marker and the route's verified flag are never read (R-11). Freshness breaks a tie only between leaders from the top-ranked producer, and only when the route permits it, so it never lets an ineligible claim win; otherwise the route surfaces the conflict, requests more context or refuses. No conflict excludes a protected item. The application supplies typed conflict groups; the assembler does not discover contradictions by interpreting prose.

Admission & fitting

Evidence goes through eight steps between the source and the payload. The first four are the producer's, and they're done before assembly starts. The last four are the assembler's, and everything it leaves out shows up in the trace with a reason code.

{{ s.n }} {{ s.name }} {{ s.text }}
4.1 Budget tiers

Every slot sits in one of three tiers. Protected items are rendered whole or the assembly is refused. Droppable items may be omitted. Compressible items may be replaced by a precomputed shorter variant or omitted. Under budget pressure that happens only once droppable items are gone; the route's versioned fitting policy orders that step, and without one, variants come before omission. The one exception is a slot the route holds at a min_tokens floor: it can keep its droppable items while other slots compress. An item over its own token_budget, or in a slot over the route's max_tokens, is reduced first, whether or not the payload fits. Every omission is traced as over_budget. The assembler never touches protected items. Only the route's versioned policy can raise a slot's tier; an item that claims a higher tier than its slot allows is excluded with tier_upgrade_not_allowed, so a producer cannot protect its own items.

5

Placement profiles

Placement is model-, task- and content-dependent. This specification takes no position on where items go. It fixes the semantic slots and requires that placement be a profile: versioned, per route, and evaluated against that route's tasks before it's promoted for deployment (R-19). The evidence for this position is collected on the Evidence page.

6

Trace & conformance tests

Every assembly emits a trace. "Debuggable" means an engineer can reconstruct and compare assembly decisions, not just read the payload. Outcome metrics ride on top: groundedness, task success, tool-call correctness, recovery behaviour, latency, cost.

Trace fields

2026-09-23 · slot caps & floors, deduplication, supersession, source diversity
  • A route may cap a slot's share of the payload with slots.<slot>.max_tokens (R-16). The cap holds whether or not the payload fits, after token_budget caps and before budget pressure; protected items alone over it refuse with protected_content_over_budget.
  • A route may hold a slot at a floor with slots.<slot>.min_tokens (R-16). Budget pressure never makes a reduction that leaves the slot below it, and freezes the slot once one is withheld; the payload then either fits or is refused with slot_floor_over_budget (R-17). A floored slot may keep droppable items while other slots compress, the one exception to R-16's tier order.
  • New R-24: a route may ask a slot for exact deduplication with slots.<slot>.dedupe: exact. After conflict resolution, an item whose body equals a kept item's body once whitespace is collapsed is excluded with duplicate_content, and excluded[].duplicate_of names the item kept. Protected items and conflict-group members are never excluded.
  • New R-25: a route may ask a slot to supersede stale observations with slots.<slot>.supersede: source. After conflict resolution and before deduplication, an item is excluded as superseded when the same authenticated producer sent an item with the same source and a later freshness; items tied for the latest instant are all kept, excluded[].superseded_by names the item kept, and protected items and conflict-group members are never excluded.
  • R-13: a retriever that drops a passage as a near-duplicate reports it in its batch's excluded list as duplicate_content, with duplicate_of naming the candidate it kept; the trace carries the row as reported.
  • New R-26: a route may cap a slot at slots.<slot>.max_per_source items per authenticated producer and source. After deduplication, the lowest-ranked items beyond the cap are excluded with source_diversity_cap; protected items and conflict-group members are never excluded and take places first.
  • R-17 separates rejection from refusal. A snapshot that fails its schemas or the snapshot checks is rejected before assembly, with no payload and no trace; refusals are outcomes of valid snapshots. A producer id may head only one batch.
  • R-16: budget.margin_percent (an integer from 0 to 100) reserves a safety margin for a tokenizer that estimates. Only the test of whether the whole payload fits scales the count by it; caps, floors and traced counts do not, and the trace's budget repeats it.
  • Conformance defines estimate-utf8/v1, a portable tokenizer that counts UTF-8 bytes divided by 4, rounded up, for models with no local tokenizer. It is meant for use with budget.margin_percent.
  • R-19 and R-21: a profile names the specification it was written for in spec (cwa/draft until the first release), a profile for another specification is rejected, and every trace repeats it in context.spec.
  • Requirement IDs stay permanent: new requirements append after R-23 rather than renumbering a section.

2026-09-22 · conflict resolution
  • R-11 defines what resolution does to the payload. Authority excludes nothing; among governing or user peers, one governs and the rest defer excludes the deferring peers (conflict_deferred). Fact policy excludes the other members (conflict_lost). No conflict excludes a protected item.
  • Route policy gains facts.<key> (precedence by authenticated producer, scope, freshness_tiebreak, on_unresolved) and on_unresolved_instruction. Surfaced members are marked in the payload.
  • conflicts[].resolution becomes resolved, surfaced, context_requested, refused or moot; an optional winner names the member that prevailed.
  • An item belongs to at most one conflict group, and groups must name candidates in the snapshot and facts the route defines.

Future work · non-normative

A future revision will describe request intent as a typed tree that items bind to, so that eligibility rules can reference the part of the request an item serves rather than the request as a whole. Machine-readable schemas and contract fixtures are available in this repository.

Two extensions wait until a producer needs them. A producer call key would let supersession (R-25) group observations by the call they answer rather than by source, so that source could name the server or tool a citation points to; supersede is an enum, so a call-key mode can join source without a new field. A cluster mode for deduplication (R-24) would collapse chunks that share a retriever-computed cluster id; until a clustering service spans producers, a retriever drops its own near-duplicates and reports each one (R-13), which keeps every exclusion in the trace. A reference assembler implementing the complete specification remains in progress; its conformance status is tracked on the Assembler page.

The eligibility predicate is closed at the slot-level rules R-3 lists. A future specification version may introduce additional eligibility rules or an extension mechanism with defined snapshot, evaluation, and conformance requirements.
